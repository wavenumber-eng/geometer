# Rust/wgpu Consumer Demonstration Proposal

User addition: create a Rust/wgpu app demonstrating the real Rust APIs. Scope
decision pending: a focused separate example or the replacement for the planned
C++/SDL GPU viewer. No Rust app or extra renderer dependency has been implemented.

## Intended Consumer Path

The Rust app owns UI/camera and wgpu GPU resources. It uses the public typed
`geometer-client` to discover/spawn a compatible native executable, negotiate
operations and request model/mesh geometry, Fast HLR and native illustration.
It does not statically link Geometer/OCCT, embed JavaScript/WASM, duplicate
illustration policy or assemble private JSON/subprocess calls. Tokio/client
work stays off the UI/render event loop; completion messages carry model/view
revision IDs and preserve stale-result/error/progress semantics.

This tests an actual consumer boundary, unlike a C++ demo that directly links
the kernel. Geometry is generated by Geometer, 3D presentation is performed
by wgpu, and illustrated SVG comes from the governed native illustration API.
If the viewer needs tessellated/colorized geometry for its GPU preview, obtain
it through a documented supported model/mesh operation or asset export. Do not
invent an ad-hoc native bridge just to get a first picture on screen.

## Visible Demonstration

- Open representative STEP bytes and show executable version, ABI/catalog
  compatibility and available capabilities.
- GPU-render a model with hardware depth, stable orbit/pan/zoom and explicit
  Fit, sharing camera/units with geometry and illustration requests.
- Select Fast HLR detail/shadow and separately view geometry versus native
  illustration output; preserve independent outline/detail layers.
- Show loading/computing/ready/error phases and elapsed time. Never imply
  active native cancellation where only queued cancellation is supported.
- Export typed geometry JSON, original vector SVG and the governed style;
  no screenshot substituted for SVG and no stale snapshot exported silently.
- Exercise unavailable-operation, invalid-model and process-failure behavior
  without requiring the user to read console output.

## Scope Choice And Platform Order

If separate, keep it focused on client API coverage and reuse fixture/output
expectations; do not duplicate the full C++ viewer's UI feature roadmap. Give
it its own optional Cargo target, locked dependencies, Rack registration and
demo audit entry. Do not add wgpu/UI dependencies to `geometer-client` itself.

If replacing, revise the main architecture, build/shader/toolchain steps and
Mac handoff to Rust/wgpu before implementation. Carry forward the dockable
left/right controls, usable resizing/DPI, results workspace, progress and
exports; choose the Rust UI/docking integration explicitly rather than assuming
Dear ImGui backend code is reusable unchanged. Retain the existing C++ example
under the user's retain-all decision, but do not implement an unnecessary new
SDL GPU viewer in parallel.

Windows remains first. Establish a macOS arm64 build for the separate Mac
agent; distinguish build success from actual GPU/UI/API behavior. The native
illustration service still needs its four-platform acceptance even if this
demo initially targets only Windows/macOS. According to the
[wgpu project](https://wgpu.rs/), native backends include DirectX 12 and Metal;
pin and test the selected versions/features rather than assuming portability.

## API Proof And Companion Python Coverage

Keep headless Rust API integration tests separate from GPU/manual tests. Validate
STEP-to-illustration and mesh inputs, typed results, SVG determinism/baseline
parity and lifecycle failures with the actual native executable. Record exact
client/executable/artifact revisions and open exported SVG independently.

The corresponding Python API is required upstream, with its own public package
example and equivalent fixture assertions. The Rust app does not substitute
for testing Python's executable wrapper. Neither client should require the
other language's GUI package to use native illustration.
